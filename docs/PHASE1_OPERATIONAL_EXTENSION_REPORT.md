# تقرير تسليم: توسعة التشغيل والرواتب — DOU Phase 1

**حالة التسليم:** جاهز للمراجعة المحلية.  
**المرجع السابق:** `baa8fac` — تطبيع التشغيل والماليات.  
**النشر:** لم يتم دفع أي تغيير إلى GitHub ولم يتم النشر إلى Render.

## الملخص التنفيذي

أضافت هذه الدفعة طبقة تشغيلية محكومة فوق البنية التي طُبّعت سابقاً، من دون إنشاء مصدر حقيقة ثانٍ للمدن أو الفروع أو الأداء أو البونص أو الرواتب. أصبح بإمكان الشركة معاينة ثم تأكيد استيراد المندوبين والأداء من CSV، وإدارة سياسات خصم الحضور ضمن أحداث خاضعة للمراجعة، والعمل بتصحيحات مالية لاحقة عند إقفال الرواتب بدلاً من تعديل سجل تاريخي. كما أضافت الدفعة مؤشرات احتياج تشغيلية، بحثاً وصفحات API للمندوبين، وتحققاً إضافياً لعزل المشرف في الوردية والحضور.

> **قاعدة النظام بعد التوسعة:** يظل `ContractBranch` مرجع التعيين، وتظل `DailyLog` مرجع الطلبات المؤهلة، ويظل محرك `financial_calculations.py` المرجع الوحيد للبونص والرواتب والإيراد والهامش. لا يحسب أي جزء من الواجهة راتباً أو بونصاً محلياً.

| المحور | النتيجة |
|---|---|
| سياسات الحضور والخصومات | **PASS** — سياسة شركة، حدث حضور، اعتماد اختياري، منع تكرار، وإدخال رواتب معتمد فقط. |
| سلامة إقفال الرواتب | **PASS** — رفض التعديل المباشر للفترة المقفلة، وتصحيح موثق في فترة مفتوحة لاحقة. |
| استيراد المندوبين | **PASS** — قالب، معاينة، أخطاء صفية، تأكيد ذري، منع تكرار الملف، وسجل دفعة. |
| استيراد الأداء | **PASS** — تحقق المندوب/المشروع/التاريخ، تحديث سجل يوم مطابق لا مضاعفة، واتساق مع البونص والرواتب والمالية. |
| عزل المشرف | **PASS** — عزل الملفات والورديات وبدء الوردية والحضور حتى عند إرسال معرف يدوي. |

| العربية والإنجليزية | **PASS (تركيب وقاموس)** — أضيفت مصطلحات الواجهة الجديدة إلى قاموس الترجمة؛ فحص JavaScript ناجح. |

## التغييرات التشغيلية والمالية

### 1. سياسة الحضور والخصومات

أُضيف نموذجان جديدان: `AttendanceDeductionPolicy` و`AttendanceEvent`. السياسة مرتبطة بالشركة وتحدد نوع الحدث، وقت السماح، طريقة الحساب، المبلغ أو المعدل، الحد الأعلى، تواريخ السريان، وحالة اعتماد اختيارية. الطرق المنفذة فعلياً هي **مبلغ ثابت** و**لكل دقيقة** و**لكل ساعة** و**اعتماد يدوي فقط**. تُحفظ كل حالة تأخير أو انصراف مبكر أو غياب كحدث مستقل ذي مفتاح تكرار، ولا يتحول إلى `PayrollAdjustment` إلا عندما يكون مسموحاً ومعتمداً.

| الحالة | السلوك المالي |
|---|---|
| لا توجد سياسة فعالة | يسجل الحدث بحالة `NO_POLICY` ولا ينشأ أي خصم. |
| سياسة تلقائية مكتملة | ينشأ تعديل راتب واحد معتمد فقط باستخدام مفتاح `attendance-event:{id}`. |
| سياسة تتطلب اعتماداً | يبقى الحدث `PENDING_APPROVAL` ولا يدخل الراتب قبل قرار إدارة الشركة. |
| رفض الحدث | يبقى بلا تعديل راتب. |
| فترة رواتب مقفلة | يحفظ الحدث كـ `BLOCKED_CLOSED_PERIOD` ولا يعدل اللقطة التاريخية. |

تتولد أحداث التأخير والانصراف المبكر من `shifts.py` بعد حساب الوقت في الخادم. الغياب لا ينشأ تلقائياً لمجرد القراءة؛ تنفذه الشركة من إجراء تسوية محدد للتاريخ بعد انتهاء الوردية. العملية قابلة للإعادة ولا تنتج تكراراً.

### 2. إقفال الرواتب والتصحيح اللاحق

يحسب محرك الرواتب التعديلات ذات الحالة `APPROVED` فقط، مع الحفاظ على التعديلات القديمة التي لا تملك حالة أثناء الترحيل. بعد إقفال `PayrollPeriod`، يرفض `POST /hr/adjustments` إدخال تعديل في الشهر نفسه برمز `409`. المسار `POST /hr/payroll/corrections` يفرض أن تشير العملية إلى فترة أصلية مقفلة، وأن تسجل في شهر مفتوح لاحق، وأن تحتوي سبباً ونوعاً ومبلغاً ومندوباً تابعاً للشركة. يبقى `PayrollSnapshot` و`OperationalFinancialSnapshot` بلا تعديل.

### 3. استيراد المندوبين

يقدم المسار `/fleet/imports/riders/template` قالب CSV، ثم يستقبل `/preview` النص المقروء من الملف ويخزن `OperationalImportBatch` بحالة `PREVIEW`. تتحقق المعاينة من الاسم والجوال وكلمة المرور الأولية والمدينة المفعلة والعقد والفرع والمشرف والحالة والقيم الرقمية. يتحقق النظام أن المشرف هو مشرف الفرع والمدينة فعلاً، ويرفض تكرار الهاتف في الملف أو قاعدة البيانات. لا ينشأ أي مندوب في المعاينة، ولا يسمح بالتأكيد عند وجود صف غير صالح.

عند `confirm`، يستخدم النظام `create_rider_record` نفسها التي تستخدمها إضافة المندوب الفردية. لذا تبقى قواعد الباقة والمدينة والفرع والمشروع والمشرف والحساب وكلمة المرور واحدة. التأكيد ذري: إما تنجح الدفعة كاملة أو يرجع كل شيء. تمنع بصمة SHA-256 لملف تم تأكيده إعادة الاستيراد غير المقصودة.

### 4. عمليات جماعية وتوسّع القائمة

أضيفت عملية `POST /fleet/couriers/bulk` لتغيير حالة مجموعة من المندوبين أو إعادة تعيينهم إلى **فرع تشغيلي**. لا يقبل النظام تغيير المشرف مستقلاً عن الفرع؛ ينتج المشرف والمدينة والمشروع من الفرع. تعمل العمليات حتى 1,000 مندوب في معاملة واحدة. التعليق يعطّل حساب المندوب ويبطل الرموز السابقة ويوقف حالته الحية.

أضيفت واجهة `GET /fleet/couriers/page` للبحث والتصفية الصفحية من SQL حسب الاسم أو الجوال أو المدينة أو الفرع أو المشرف أو المشروع أو حالة التوظيف أو الاتصال أو المستندات، بحد أقصى 200 نتيجة لكل صفحة. يحافظ `GET /fleet/couriers` على توافق الواجهة القديمة.

### 5. استيراد الأداء ومصدر المالية

يستخدم استيراد الأداء `DailyLog`، وهو مصدر الطلبات المؤهلة القائم. يتحقق CSV من جوال المندوب وتبعيته للشركة وتاريخه غير المستقبلي ومشروعه الحالي وعدد الطلبات غير السالب. المفتاح التشغيلي هو `(courier_id, project_id, log_date)`؛ السجل القائم يحدّث **بقيمة التقرير الجديدة** بعد تحذير المعاينة ولا تضاف الأرقام فوقه. تحفظ الحقول `source_type` و`source_batch_id` و`source_row_key` أثر مصدر الملف.

البونص والراتب وكشف الشركة وإيراد العميل وهامش التشغيل يقرأون السجل نفسه بعد التأكيد. لا يعرض تطبيق المندوب اسم العميل أو سعره أو الإيراد أو الهامش؛ يعرض فقط مكونات مستحقه وصافي المعاينة أو اللقطة المقفلة.

### 6. الاحتياج والتدقيق والواجهات

أضيف `/fleet/needs-attention` لتجميع حالات العمل من البيانات الموجودة: الغياب بعد تسوية الحضور، التأخير، المندوبون بلا فرع أو مشرف، المستندات الحرجة، خصومات الحضور المعلقة، دفعات الاستيراد ذات الأخطاء، وفترة الراتب غير المقفلة. القراءة لا تنشئ أي حدث أو خصم.

تستخدم لوحة الشركة بطاقات HR القائمة لإظهار الاحتياج، معاينة/تأكيد استيراد المندوبين، معاينة/تأكيد استيراد الأداء، السياسات، وأحداث الحضور. أضيفت ترجمة المصطلحات الجديدة إلى `i18n.js`. يقرأ تطبيق المندوب ملخصه الشخصي من `PayrollSnapshot` للفترة المقفلة وإلا من `calculate_payroll_preview`.

## قاعدة البيانات والترحيل

| الكيان أو الحقل | الغرض | سلامة الترحيل |
|---|---|---|
| `attendance_deduction_policies` | سياسة خصم حضور الشركة | جدول إضافي فقط. |
| `attendance_events` | حدث حضور قابل للمراجعة ومفتاح تكرار | جدول إضافي وفهارس شركة/حالة/تاريخ. |
| `operational_import_batches` | معاينة وتأكيد ونتيجة وبصمة دفعات CSV | جدول إضافي وقيد بصمة شركة/نوع. |
| `payroll_adjustments.status` | إدخال المعتمد فقط في الراتب | عمود إضافي بقيمة افتراضية `APPROVED`. |
| `daily_logs.source_*` | تمييز مصدر الأداء والدفعة وصف الصف | أعمدة إضافية فقط. |
| فهارس جديدة | أحداث الحضور والدفعات ومصدر الأداء | إنشاء مشروط وآمن في PostgreSQL. |

تنفذ `Base.metadata.create_all` الجداول الجديدة عند تشغيل التطبيق، وتضيف `run_migrations` الأعمدة والفهارس المفقودة دون حذف أو إعادة ضبط أي بيانات.

## قرارات عمل مطلوبة قبل التوسع التالي

| القرار | السبب |
|---|---|
| قاسم الراتب اليومي لقاعدة «نسبة الراتب اليومي» | لا يمكن تنفيذ طريقة يومية عادلة من دون تعريف أيام الراتب أو أيام العمل في الشركة. لذلك لم تُعرض كطريقة حساب. |
| من يملك سلطة إقفال الراتب وتعريف بداية ونهاية الفترة | النظام يقفل شهراً تقويمياً حالياً؛ أي دورة رواتب مختلفة تتطلب إعداداً صريحاً. |
| مصدر «الطلب المكتمل تجارياً» | `DailyLog` مصدر أداء تشغيلي مؤهل، وليس تأكيداً مستقلاً من نظام العميل أو API. |
| سياسة سعر العميل المؤرخ تاريخياً | تغيير سعر العميل اللاحق لا يعيد كتابة اللقطة المقفلة، لكن قواعد العقود الفعلية للتغيير تحتاج اعتماداً تشغيلياً. |
| مصالحة ملفات أداء العميل بعد الإقفال | النظام يرفض تعديل الفترة المقفلة؛ التصحيح الآن يذهب لفترة لاحقة ويحتاج اعتماداً محاسبياً داخلياً. |

## بنود لم تُنفذ عمداً

لم يُفعّل أي مسار من Phase 2 أو نظام طلبات قديم غير مفعّل. لم تنشأ خصومات تلقائية بلا سياسة. لم يُستخدم سعر العميل لحساب مستحق المندوب. لم تُبنَ محاسبة مزدوجة أو تحويلات أموال أو رصيد مالي. لم يجر نشر أو دفع التغييرات.
