# تقرير هندسي: تطبيع بنية التشغيل والمالية — Phase 1

**النظام:** DOU Fleet Partners

**النطاق:** مسار التشغيل الحي للشركة والمندوب في Phase 1 فقط

**إعداد التقرير:** Manus AI

**حالة التسليم:** جاهز لمراجعة التزام Git محلي واحد؛ **لم يتم الدفع إلى GitHub ولم يتم النشر إلى Render**.

> يطبع هذا العمل نموذج المدينة، والعقد التجاري، وتعويض المندوب، والبونص، والرواتب، والإيراد، وهامش التشغيل من دون تغيير إطار FastAPI أو إعادة تصميم الواجهة أو تمكين المسارات القديمة المحجوبة بالراية `ENABLE_LEGACY_DELIVERY`.

## 1. النتيجة التنفيذية: قبل وبعد

قبل هذا العمل، كانت المدينة قيمة نصية موزعة بين الملف والفرع والعقد، وكان العقد التجاري يخلط بين سعر العميل وتعويض المندوب. كما كانت عدة مسارات تعيد حساب البونص والراتب بشكل مختلف، ولم يكن هناك إقفال لفترة الرواتب أو سجل مالي نهائي قابل للمراجعة. أما الآن فأصبحت طبقة التشغيل قائمة على مدن مفعلة لكل شركة وفروع مرتبطة بها، وفصل صريح بين إيراد العميل وتعويض المندوب، ومحرك مالي واحد للمعاينة والإقفال.

| المجال | قبل التطبيع | بعد التطبيع |
|---|---|---|
| مدينة التشغيل | نصوص حرة في `Courier.work_city` و`Courier.zone` و`ContractBranch.city`. | `GeoCity` مرجع عام مع `TenantOperatingCity` لتفعيل المدينة للشركة؛ ويرتبط الفرع والمندوب بـ`city_id`. |
| الفرع والتعيين | العلاقة موجودة لكن المدينة والمشرف والمشروع قد تتعارض عبر حقول مكررة. | فرع العقد هو مصدر التعيين التشغيلي؛ وتُشتق المدينة والمشرف والمشروع في تعديل أو إنشاء المندوب. |
| العقد | العقد التجاري يحوي حقول راتب وأجر توصيلة، ما يخلط الاتفاق التجاري بتعويض المندوب. | `client_name` و`client_rate_per_order` حقول تجارية صريحة؛ وتبقى تعويضات المندوب في ملفه أو عقد تعويض قديم متوافق. |
| البونص | اختيار خطة البونص وحسابها مكرر في HR والأسطول والتطبيق. | خدمة موحدة تختار تجاوز المندوب أولاً ثم خطة الفرع الفعالة، وتحسب الطلبات المؤهلة والبونص. |
| الرواتب | معاينة مباشرة قابلة لإعادة الحساب، بلا فترة مغلقة أو لقطات نهائية. | `PayrollPeriod` و`PayrollSnapshot` يسجلان الإقفال الشهري؛ القراءة بعد الإقفال تأتي من اللقطات. |
| الإيراد والهامش | استخدام أو عرض قيم طلبات قديمة لا تمثل اتفاق العميل. | الإيراد = الطلبات المؤهلة × سعر العميل؛ هامش التشغيل = الإيراد − التكلفة المباشرة للمناديب. |
| الواجهة | نموذج العقد يخلط التعويض التجاري وتعويض المندوب، ولا توجد إدارة للمدن أو إقفال للرواتب. | بطاقة مدن تشغيل، قائمة فروع مبنية على مدن مفعلة، حقول عميل/سعر طلب، بطاقات إيراد/هامش، وزر إقفال الرواتب للمدير فقط. |

## 2. تغييرات قاعدة البيانات

كل التغييرات **إضافية وآمنة**. لا توجد إعادة تهيئة لقاعدة البيانات ولا حذف لبيانات قائمة. تظل الحقول النصية والحقول القديمة متاحة للتوافق والعرض خلال الانتقال.

| الكيان أو الجدول | التغيير | الغرض التشغيلي |
|---|---|---|
| `TenantOperatingCity` | جدول جديد يربط الشركة بـ`GeoCity` مع حالة تفعيل واسم عرض. | يمنع استخدام مدينة غير مفعلة للشركة مع الإبقاء على مرجع مدينة عام موحد. |
| `Courier` | `city_id` مع فهارس نطاق الشركة/المدينة/المشرف. | ربط المندوب بمدينة مرجعية عبر فرع التشغيل بدلاً من المطابقة النصية. |
| `ContractBranch` | `city_id`. | الفرع يرتبط بمدينة مرجعية ويحتفظ بحقل `city` للعرض والتوافق. |
| `Contract` | `client_name` و`client_rate_per_order` و`client_rate_effective_from`. | فصل اتفاق العميل وإيراد الشركة عن راتب المندوب وأجر التوصيلة. |
| `BonusPlan` | `is_active` و`effective_from` و`effective_to`. | دورة حياة لخطة البونص، مع تعطيل آمن بدلاً من الحذف. |
| `PayrollAdjustment` | `idempotency_key` و`source_type` و`source_id`. | قابلية ربط أي تعديل بمصدره ومنع تكرار الإدخال عند ربطه بمصدر مستقبلاً. |
| `PayrollPeriod` | جدول جديد لفترة شهرية وحالة الإقفال. | تعريف الحالة الرسمية لفترة الراتب. |
| `PayrollSnapshot` | جدول جديد للنتيجة النهائية لكل مندوب وفترة، مع فرع العقد. | منع التعديل الرجعي الصامت للرواتب بعد الإقفال. |
| `OperationalFinancialSnapshot` | جدول جديد للطلبات المؤهلة والإيراد وتكلفة المندوب والهامش لكل فرع وفترة. | سجل نهائي للإيراد والهامش التشغيلي على مستوى الفرع. |

أضيفت ترقيات الأعمدة والفهارس في `app/migrations.py` باستخدام نمط آمن لإعادة التنفيذ. يبدأ التطبيق بترحيل محافظ للمدن الموجودة من النص إلى المرجع حين تكون المطابقة غير ملتبسة؛ ولا يحوّل القيم غير المؤكدة قسراً.

## 3. منطق الأعمال ومصادر الحقيقة

يوجد الآن مصدر حساب موحد في `app/services/financial_calculations.py`. يحسب المحرك الطلبات المؤهلة من `DailyLog` ضمن الشهر ونطاق مشروع المندوب، ثم يختار خطة البونص الفعالة. أولوية الاختيار هي خطة تجاوز خاصة بالمندوب ثم خطة الفرع العامة، مع احترام حالتي التفعيل والفترة الفعالة. يستخدم كل من كشف الرواتب، وتقرير البونص، وملف المندوب، وسجل تطبيق المندوب، والتقرير اليومي الدوال نفسها أو واجهة حساب متوافقة لها.

| القيمة | مصدر الحقيقة الحالي | قاعدة الحساب |
|---|---|---|
| المدينة المسموح بها | `TenantOperatingCity` + `GeoCity` | لا يُنشأ أو يُعدّل فرع أو تعيين مندوب على مدينة غير مفعلة للشركة. |
| التعيين التشغيلي | `ContractBranch` | الفرع يحدد العقد والمدينة والمشروع والمشرف؛ هذه الحقول تُنشر إلى ملف المندوب عند إعادة التعيين. |
| الطلبات المؤهلة | `DailyLog` | مجموع غير سالب لطلبات المندوب في الشهر وعلى مشروعه التشغيلي الحالي. |
| خطة البونص | `BonusPlan` | تجاوز المندوب الفعال، وإلا خطة الفرع الفعالة؛ لا تعتمد خطة موقوفة أو خارج نافذة تاريخها. |
| البونص | محرك الحساب الموحد | عند الوصول للتارجت: مبلغ التارجت + (الطلبات الزائدة × سعر الطلب الزائد). |
| راتب المندوب | ملف المندوب أو عقد تعويض قديم صريح | راتب ثابت + أجر توصيل للطلبات المؤهلة + بونص + إضافات − خصومات. |
| إيراد العميل | العقد التجاري | الطلبات المؤهلة × `client_rate_per_order`. |
| هامش التشغيل | التقرير المالي للفرع | إيراد العميل − صافي تكلفة المناديب المباشرة في الفرع. |

لا تعتمد نظرة عامة الأسطول على `Order.total` لتمثيل إيراد العقد. تعرض الآن إجمالي الرواتب التقديري وإيراد العميل التقديري وهامش التشغيل التقديري من المحرك المالي. لا تظهر بيانات مالية تجارية للمشرف من مسار التقرير المالي للشركة؛ يظل نطاقه مقصوراً على فريقه التشغيلي.

## 4. الهجرة والتوافق التشغيلي

مسار الهجرة مصمم ليكون آمناً لقاعدة Render القائمة وقابلاً للتشغيل المتكرر.

| خطوة | السلوك | حماية البيانات |
|---|---|---|
| إضافة الجداول والأعمدة | ترقية إضافية في `migrations.py`. | لا حذف ولا تغيير نوع مدمر. |
| استرداد المدن | `backfill_operating_cities()` عند البدء. | يربط فقط المطابقات النصية غير الملتبسة؛ الباقي يظل واضحاً للمراجعة. |
| العقود السابقة | حقول التعويض القديمة باقية. | لا تُفقد بيانات التعويض السابقة؛ العقود التجارية الجديدة لا تستخدمها لإيراد العميل. |
| الفروع والمندوبون | تبقى حقول العرض النصية (`city` و`work_city`) مملوءة. | الشاشات والتقارير القديمة تستمر في العرض أثناء تحوّل العلاقات إلى معرّفات. |
| خطط البونص السابقة | حقول دورة الحياة لها قيم متوافقة؛ والحذف صار تعطيلًا آمناً. | لا تُمحى خطة يمكن أن تكون ذات صلة بسجل أو فترة. |
| الرواتب قبل الإقفال | تظل معاينة حية. | لا يُدّعى أنها تاريخ نهائي حتى يطلب مدير الشركة الإقفال. |
| الرواتب بعد الإقفال | تقرأ الرواتب والبيانات المالية من اللقطات. | تعديل يومي لاحق أو تعديل يدوي لاحق لا يغيّر نتيجة الفترة المقفلة. |

## 5. الواجهة وتجربة الاستخدام

حُفظت أنماط البطاقات والجداول والنوافذ الموجودة، ولم تُعد هندسة التصميم. تتيح لوحة الموارد البشرية إدارة مدن التشغيل في بطاقة ونموذج صغيرين، وتستخدم نافذة العقد قائمة مدن تشغيل مفعلة بدلاً من كتابة المدينة الحرة. تظهر في العقد حقول اسم العقد التشغيلي، العميل أو المنصة، وسعر الطلب من العميل مع توضيح أنه **إيراد الشركة وليس أجر المندوب**.

أضيفت بطاقات نظرة عامة لإجمالي الرواتب التقديري وإيراد العميل التقديري وهامش التشغيل التقديري. كما أضيف زر إقفال رواتب الشهر لحسابات مالك الشركة أو مدير النظام فقط؛ ويعرض حالة واضحة للمعاينة أو الفترة المقفلة. زاد إصدار ملف الترجمة في `fleet.html`، وأضيفت مفردات المدن والإيراد والهامش والإقفال إلى `static/i18n.js`.

## 6. الاختبارات والتحقق

تمت الاختبارات على قواعد SQLite معزولة، منشأة من بيانات البذرة، ولم تُستخدم قاعدة Render أو أي حساب إنتاجي.

| الاختبار | النتيجة | ما الذي تحقّق منه |
|---|---|---|
| `python3 -m py_compile` للملفات الخلفية والخدمات والاختبارات الجديدة | PASS | سلامة تركيب Python لكل الملفات المعدلة الأساسية. |
| `node --check static/i18n.js` واستخراج نص JavaScript من `fleet.html` ثم فحصه | PASS | سلامة JavaScript للترجمة ولوحة الشركة. |
| `tools/test_supervisor_scope.py` | PASS — 21 فحصاً | عزل المشرف من الخادم، منع الوصول المباشر لفريق آخر، وتحديث نطاق الفريق. |
| `tools/test_shift_attendance_flow.py` | PASS | إسناد الوردية، حضور المندوب، الإسناد إلى الوردية، وحساب نافذة الوردية الليلية. |
| `tools/test_company_operations_edit.py` | PASS | مدينة تشغيل، عقد تجاري، تعديل فرع/مشرف، تحديث المندوب، وتجدد صلاحية الوصول. |
| `tools/test_phase1_business_lifecycle.py` | PASS | مدينة → عقد/فرع → مندوب → سجل طلبات → بونص → تعديل → معاينة راتب/ماليات → إقفال → ثبات اللقطات. |
| `python3 -m pytest tools/ -v` | PASS | تشغيل حزمة أدوات الاختبار بلا أخطاء جمع؛ توجد تحذيرات قديمة خاصة بـ`utcnow` ودورة مفاتيح SQLite فقط. |
| فحص واجهة الدخول المحلية بالعربية | PASS | النصوص العربية واتجاه RTL يظهران في صفحة الدخول المحلية. |
| فحص واجهة الدخول المحلية بالإنجليزية | PASS | محتوى صفحة الدخول المستخرج بالإنجليزية فقط؛ التفاصيل في `docs/ui_localization_validation.md`. |

> تعذر الحصول على لقطة متصفح بعد الضغط على دخول لوحة محلية بسبب انقطاع جلسة المتصفح مرتين؛ لذلك سُجلت هذه النقطة بصفتها قيداً في التحقق البصري فقط. لم يؤثر ذلك في اختبارات API أو فحوص JavaScript، وكلاهما نجح.

## 7. قواعد أعمال مطلوبة قبل أي توسع لاحق

هذه البنود **لا يجب تخمينها أو تفعيلها آلياً**. لم تُنفذ خصومات أو سياسات بديلة لها في هذا التغيير.

| قرار مطلوب من الشركة | سبب الإلزام | الحالة الحالية |
|---|---|---|
| سياسة خصم الغياب والتأخير والانصراف المبكر | لا يوجد مبلغ أو نسبة أو عتبة أو سلطة اعتماد مضبوطة. | لا تُنشأ خصومات حضور تلقائية. |
| مصدر الطلب المكتمل المؤهل لإيراد العميل | `DailyLog` سجل تشغيل يدخله المندوب، وليس تأكيد تسليم تجارياً موثقاً من منصة العميل. | يستخدم مؤقتاً كقاعدة Phase 1 مع تنبيه تشغيلي صريح. |
| سياسة سريان سعر العميل التاريخي | تغيير السعر خلال شهر أو لفترة سابقة يحتاج تعريفاً لمتى يبدأ السعر وكيف يعامل السجل غير المقفل. | تغيير السعر يضبط تاريخ السريان الحالي؛ اللقطة المقفلة تحفظ النتيجة النهائية. |
| سلطة وفترة إقفال الرواتب | يلزم تحديد من يملك الإقفال وما إذا كانت الفترة شهرًا ميلاديًا كاملاً ومعالجة إعادة الفتح. | الإقفال متاح لمالك الشركة/مدير النظام؛ إعادة فتح الفترة غير منفذة. |
| تصنيفات الإضافات والخصومات ومصدرها | السلفة والإضافات تحتاج سياسة اعتماد ومحاسبة وربطًا بمصدر موثق. | يدعم النموذج مفاتيح المصدر والمعرّف التكراري، لكن لا توجد سياسة موحدة لكل الأنواع. |

## 8. المسائل المتبقية والحدود المعروفة

العمل لا يفعّل المسارات القديمة (`analytics` و`orders` و`merchants` و`geo`) ولا يجعلها مصدراً مالياً؛ ما زالت محجوبة في المسار الحي. لا يتحول `DailyLog` إلى إثبات تسليم تجاري بمجرد التطبيع، ولذلك يجب ألا يستخدم كبيان فوترة خارجي قبل اعتماد مصدر طلبات مكتمل من العميل أو المنصة.

لا توجد سياسة لإعادة فتح فترة رواتب مقفلة أو إنشاء تسوية لاحقة مرتبطة بلقطة قائمة؛ هذه خاصية محاسبية تتطلب قرار أعمال واضحاً. كذلك لا يوجد تطبيق لخصم الحضور أو لتسوية ضرائب أو رسوم أو التزامات قانونية. وأخيراً، بقيت تحذيرات `datetime.utcnow()` ودورة المفاتيح المرجعية في SQLite في حزمة الاختبارات؛ وهي تحذيرات تقنية قائمة وليست أخطاء تشغيلية في هذا التغيير.

## خلاصة المراجعة

التطبيع المنفذ يحقق مساراً واحداً ومراجعاً لمدينة التشغيل، وتعيين المندوب، وخطة البونص، والراتب، وإيراد العميل، وهامش التشغيل. يحافظ على بيانات العرض القديمة وتوافق الوظائف السابقة، ويضيف تاريخاً مالياً مقفلاً بدلاً من إعادة حساب صامتة. التزام Git المجهز بعد هذا التقرير مناسب للمراجعة اليدوية فقط، وفق القيد المطلوب بعدم الدفع أو النشر.
