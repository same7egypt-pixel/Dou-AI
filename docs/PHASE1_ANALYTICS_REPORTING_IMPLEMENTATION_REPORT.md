# تقرير تنفيذ وقبول تحليلات وتقارير DOU — Phase 1

**الحالة:** مكتمل محلياً وجاهز للمراجعة. لا يتضمن هذا العمل أي دفع إلى GitHub أو نشر إلى Render أو تعديل لبيانات الإنتاج.

## 1. النطاق والقرار المعماري

نُفذت تجربة تقارير احترافية ومحدودة النطاق داخل قسم التقارير القائم في `fleet.html`. أضيفت أربع تجارب قراءة فقط: **لوحة الإدارة، التشغيل، المالية، والقوى العاملة والأداء**. لم تُعد كتابة منطق البونص أو الراتب أو الإيراد أو الهامش؛ بل تستخدم طبقة التقرير مصادر الحقيقة الموجودة في Phase 1 كما وثق تدقيق ما قبل التنفيذ في [`PHASE1_ANALYTICS_REPORTING_AUDIT.md`](PHASE1_ANALYTICS_REPORTING_AUDIT.md).

> لا ينشئ التقرير سجلات حضور أو أداء أو رواتب أو تعديلات، ولا يعتمد على القيمة الظاهرة في المتصفح لحساب أي KPI أو مبلغ مالي.

| مجال التقرير | مصدر الحقيقة المستخدم | طريقة العرض |
|---|---|---|
| الطلبات المؤهلة | `DailyLog` ضمن فترة التشغيل المختارة | تجميع خادمي وفق `tenant_id` وعلاقات المندوب/المشروع. |
| الحضور وساعات العمل | `Attendance` و`AttendanceEvent` | أيام الحضور، الساعات المسجلة، التأخير، الانصراف المبكر والغياب. |
| التارجت والبونص | `calculate_courier_bonus` | وضع الشهر حتى تاريخ نهاية التقرير، من خطة البونص السارية. |
| الرواتب | `payroll_rows` ثم `courier_financial_rows` | معاينة مركزية للفترة المفتوحة أو `PayrollSnapshot` للفترة المقفلة. |
| إيراد العميل والهامش | `financial_rows` ثم `courier_financial_rows` | مصدره عقد العميل ولقطة الفرع النهائية عند الإقفال. |
| التنبيهات التنفيذية | `/fleet/needs-attention` القائم | يعاد استخدامه في لوحة الإدارة ولا يعاد احتسابُه. |

## 2. ما نُفذ

أضيفت خدمة `app/services/reporting.py` كطبقة تركيب قراءة فقط. تطبق نطاق الشركة أو نطاق الفريق أولاً، ثم تطبق الفلاتر المعرفية، ثم تعرض KPI ورسومات موجزة وصفوفاً مفصلة مصفحة. كما أضيف مخرج قراءة مالي تفصيلي `courier_financial_rows` داخل المحرك المالي القائم نفسه. هذا المخرج لا يقدم معادلة جديدة؛ إنه يركب صف الراتب المركزي مع صف الفرع/اللقطة المالية المركزي فقط.

| التجربة | المخرجات الرئيسية | الضوابط |
|---|---|---|
| لوحة الإدارة | عدد النشطين والمتصلين، الطلبات، الحضور، تحقيق التارجت، تكلفة البونص والرواتب، إيراد العميل، الهامش، الرسوم والتنبيهات | متاحة لحسابات الشركة فقط لأنها تجارية. |
| التشغيل | الطلبات حسب المدينة والمشروع والمشرف، الحضور، الساعات، الطلبات لكل ساعة، التأخير، الغياب، الانصراف المبكر | لا يعرض إيراد العميل أو الهامش. |
| المالية | العميل والعقد والفرع، الطلبات المؤهلة، عناصر تكلفة المندوب، الراتب، البونص، الإضافات، الخصومات، الإيراد والهامش | متاحة لحسابات الشركة فقط. تعرض الحالة `OPEN_PREVIEW` أو `CLOSED_FINAL`. |
| القوى العاملة والأداء | المندوب والفرع والمشرف، الإنتاجية، التارجت، الحضور، المستندات، الشريحة، وتكلفة الراتب فقط عند امتلاك صلاحية payroll | لا يعرض أرقام العميل أو الهامش. |

## 3. الصلاحيات وعزل البيانات

تستخدم جميع المسارات الجديدة `TENANT_ROLES` و`reports` permission، ثم `_scope` للتحقق من الاشتراك والنطاق، ثم `_supervisor_courier_scope` داخل الاستعلام الخادمي. لذلك لا يمكن أن توسع فلاتر `city_id` أو `branch_id` أو `supervisor_id` أو `rider_id` نطاق مشرف خارج فريقه.

| الدور | التقارير المتاحة | القيود |
|---|---|---|
| Company / Company Admin | الإدارة والتشغيل والمالية والقوى العاملة والتصدير حسب الصلاحية القائمة | نطاق الشركة فقط. |
| HR / Accountant | التشغيل والقوى العاملة والراتب حيث تمنح سياسة الدور `payroll` | لا توجد واجهة أو API للإيراد التجاري أو الهامش. |
| Supervisor | التشغيل والقوى العاملة لفريقه فقط | يرفض API لوحتي الإدارة والمالية والتصدير المالي؛ لا تظهر قيم تجارية أو رواتب زملائه. |
| Project Manager | التشغيل ضمن مشاريع حسابه الحالية | لا توسع الفلاتر نطاق المشاريع المدارة. |

تغطي اختبارات القبول محاولات مشرف لإرسال معرف مدينة وفرع ومشرف تابعين لفريق آخر، ونتيجتها قائمة فارغة داخل نطاقه؛ كما تغطي رفض المالية ولوحة الإدارة وتصدير المالية برمز `403`.

## 4. الفلاتر والتوسع

تستخدم الفلاتر المعرفات المطبعة فقط: المدينة، العقد، المشروع، الفرع، المشرف، المندوب، حالة التوظيف، حالة الاتصال، البحث، والفترة. يعيد `/fleet/analytics/filters` خيارات متدرجة من نطاق المستخدم قبل عرضها. تعرض الواجهة أول 200 مندوب اختياراً لمنع تحويل القائمة إلى حمولة كبيرة، بينما يدعم البحث التفصيلي والصفحات الخادمية.

أضيفت فهارس إضافية قابلة لإعادة التشغيل في `migrations.py` وفي تعريفات النماذج، دون تعديل أو حذف أي سجل قائم.

| الفهرس | الغرض |
|---|---|
| `ix_daily_logs_tenant_date_project` | تجميع الطلبات المؤهلة حسب الشركة والتاريخ والمشروع. |
| `ix_payroll_snapshot_tenant_period_branch` | قراءة لقطة المندوب من فترة مقفلة ضمن فرع. |
| `ix_financial_snapshot_tenant_period_project` | تجميع اللقطة التجارية المقفلة حسب فترة/مشروع. |

تستخدم الواجهة 50 صفاً للصفحة وتسمح حتى 5,000 صف للتصدير الخادمي المصرح فقط. لا يتم تحميل التصدير أو الجداول الضخمة كاملة إلى DOM المتصفح.

## 5. حالة الإقفال ودلالة الأرقام

تعلن الاستجابة وواجهة التقرير صراحة ما إذا كانت المالية **معاينة فترة مفتوحة** أو **نهائية من لقطة مقفلة**. لا يسمح التقرير بإظهار إيراد أو هامش سابق من إعدادات اليوم بعد إقفال الفترة، لأن `financial_rows` يقرأ `OperationalFinancialSnapshot` ولأن الراتب يقرأ `PayrollSnapshot`.

> فترة التقرير التشغيلي قد تكون أي نطاق تاريخي. قيم الرواتب والإيراد والهامش هي قيم شهر الرواتب المرتبط بتاريخ نهاية التقرير، وتظهر الواجهة ذلك بوضوح كـ«معاينة شهرية» أو «لقطة نهائية». يجب اعتماد سياسة فترة مالية موحدة إذا أُريدت مقارنة مالية تتجاوز شهراً واحداً.

## 6. تجربة الواجهة والترجمة

استُبدل مركز التقارير القديم داخل قسمه فقط، دون إعادة تصميم بقية لوحة الشركة. التجربة الجديدة تضم تبويبات واضحة، فلاتر موحدة، أزرار اليوم/أمس/آخر 7 أيام/الشهر الحالي/السابق/المخصص، حالات تحميل ورفض وصفر نتائج، KPI قابلة للتدقيق، رسوم بسيطة لا توحي بدقة زائفة، وجدول مفصل مع صفحات وتصدير CSV عند السماح.

أضيفت ترجمة كاملة للنصوص الجديدة في `static/i18n.js`. فحص `test_analytics_i18n.mjs` يثبت أن العناوين وحالة الفترة المالية وحالات الشريحة والمستندات الديناميكية تتحول للإنجليزية ضمن آلية الترجمة القائمة.

## 7. قبول الدقة والتكامل

نفذ اختبار `tools/test_analytics_reporting.py` على قاعدة SQLite معزولة ومهيأة من بيانات المشروع. أنشأ مدينتين وعقدين وفرعين ومشرفين وثلاثة مندوبي قبول عبر قالب الاستيراد المهني، ثم تحقق من المسار التالي:

| نقطة القبول | النتيجة |
|---|---|
| `25 + 30 = 55` طلباً | ظهر الرقم نفسه في الإدارة والتشغيل والقوى العاملة وسجل المندوب وكشف الرواتب. |
| `500` طلب | بونص `1,800` وإيراد `5,000` وهامش `2,200` وفق المصادر المركزية. |
| `550` طلب | بونص `2,050` وإيراد `5,500` وهامش `2,450` وفق المصادر المركزية. |
| الفلاتر المتدرجة | المدينة قيدت الفرع والمشرف والمندوبين للمدخلات الصحيحة فقط. |
| الصفحات | اختبار صفحة خادمية بحجم صف واحد مع حفظ العدد الكلي. |
| RBAC | رفضت الإدارة والمالية والتصدير المالي للمشرف؛ رفضت الفلاتر المعبوثة الوصول لفريق آخر. |
| الإقفال | تحولت المالية إلى `CLOSED_FINAL` بعد إقفال الرواتب، وبقي البونص النهائي `2,050`. |
| CSV | تصدير مالي للشركة فقط ويحتوي حقول الإيراد والهامش المسموحين. |

## 8. نتائج الانحدار

اجتازت حزمة الانحدار المعزولة جميع التدفقات السابقة والاختبارات الجديدة: صلاحيات المشرف، الورديات والحضور، تعديل الشركة، دورة الأعمال، سياسة الحضور، استيراد المندوبين، استيراد الأداء، قبول أداء المندوب، تزامن تطبيق المندوب، عزل ورديات المشرف، قبول التحليلات، وترجمة الواجهات. كما اجتازت ملفات Python فحص التركيب، واجتاز JavaScript المضمن وفاحص `i18n.js` فحص التركيب.

## 9. قواعد أعمال مطلوبة ولم تُخترع

لم يضف هذا العمل أي سياسة خصم أو عقد أو بونص جديد. تبقى القرارات التالية مطلوبة من جهة الأعمال قبل أي تغيير مستقبلي:

| القرار المطلوب | سبب عدم افتراضه |
|---|---|
| مصدر طلب تجاري مكتمل ومتحقق | `DailyLog` مصدر Phase 1 التشغيلي وقد يكون إدخالاً من المندوب. |
| تاريخ سريان سعر العميل للسجلات المفتوحة | اللقطة المقفلة تحفظ التاريخ؛ الفترة المفتوحة تستخدم التعاقد الحالي. |
| تعريف دقيق لمقارنة مالية متعددة الأشهر | التقرير يوضح حالياً شهر مالية تاريخ النهاية لتجنب مزج فترة تشغيلية وحساب مالي غير معرّف. |
| سياسة حضور/خصم | الخدمة الحالية لا تطبق خصماً إلا وفق سياسة حاضرة واعتمادها، ولا تستنتج معدلاً جديداً. |
